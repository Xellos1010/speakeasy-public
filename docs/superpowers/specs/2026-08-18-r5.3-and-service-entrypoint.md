# R5.3 wiring + service entry-point — mini-spec

Status: DRAFT, routes back to SpeakEasy-Advisor before any implementation. Written after
reading speakeasy/app.py and speakeasy/__main__.py in full.

## Finding: R5.3 (duplicate-injection guard) is satisfied by construction — no Controller change needed

`Controller._process()` (app.py:213-257) calls `self.engine.transcribe(samples)` exactly once,
synchronously, and uses its return value directly. `RemoteFallbackEngine.transcribe_ex()`
(already implemented, feat/spk-network-service) is **sequential, not hedged**: it blocks on
the remote HTTP call with `timeout=deadline_s`, and on any failure (including a timeout)
closes that connection and falls back to local — all within the same synchronous call, in the
same thread. There is no point where a remote response can arrive *after* local fallback has
already run and produced a result: once the socket read times out, the connection is closed
and abandoned; a packet that happens to arrive a moment later has nowhere to be delivered to
(the socket is gone), so it can never reach the JSON-decode step, let alone trigger a second
injection.

R5.3's language ("a cancelled remote call whose response arrives late is discarded by
utterance id") describes a *hedged-request* design (fire remote + start a local timer that
independently kicks off local transcription, racing the two). That is not what got built, and
per the ADJ-SPK-011 wire contract (§4 in the service spec) it doesn't need to be: `Controller`
only ever sees one `Engine.transcribe()` call return one result, whichever source it came
from. **Conclusion: `speakeasy/app.py` requires no changes for R5.3.** The utterance-id check
inside `_call_remote` (rejects a response whose id doesn't match what was sent) is the only
dedup mechanism that exists, and it's sufficient for this sequential design — it exists to
reject a wrong/stale response on a reused connection, not to arbitrate a race that can't occur
here.

If a future revision moves to a genuinely hedged/streaming design (noted as out of scope in
the service spec §7), this finding would need revisiting — flagging that dependency now so it
isn't silently invalidated later.

## Wiring scope: `__main__.py` only, not `app.py`

`speakeasy/__main__.py:45` calls `create_engine(settings.engine, base / "models")` and passes
the result straight to `Controller(engine=engine, ...)` at line 100. Since
`RemoteFallbackEngine` implements the same `Engine` protocol (`transcribe`/`transcribe_ex`),
the entire wiring change is: **conditionally wrap `create_engine()`'s return value** in a
`RemoteFallbackEngine` before it reaches `Controller`, when the settings' ranking config names
any host besides `self`. When ranking is `["self"]` only (the default / single-host case),
`create_engine()`'s plain result is used unwrapped — zero behavior change for anyone not
opting into multi-host.

Concretely, proposed (not yet implemented):
```python
local_engine = create_engine(settings.engine, base / "models")
ranking = load_ranking(settings.inference_ranking)
if ranking != [SELF]:
    reachability_cache = ReachabilityCache()
    peer_cache = PeerIdentityCache(refresh_fn=default_tailscale_peers)
    prober = TailnetProber(remote_hosts=[h for h in ranking if h != SELF],
                            health_check_fn=..., peer_cache=peer_cache,
                            reachability_cache=reachability_cache)
    prober.start()  # lifecycle: stopped on app exit (needs a shutdown hook -- see open Q below)
    engine = RemoteFallbackEngine(local_engine, ranking, reachability_cache,
                                   settings.host_addresses, local_settings_record)
else:
    engine = local_engine
controller = Controller(engine=engine, ...)  # unchanged from here on
```

`health_check_fn` needs a real implementation (a `GET /health` HTTP call per host, short
timeout) — straightforward, not written yet, flagging as part of this wiring, not a new
design question.

## Open question: service entry point (not yet decided)

This box acting as an inference *host* (serving `/transcribe` to other hosts) and this box
acting as a dictation *client* (potentially calling out to another host) are separate
concerns that happen to run on the same machine simultaneously. The client side wires into
`__main__.py` per above. The server side (`speakeasy/service.py`'s `run_server`) needs its own
process lifecycle — three options, not chosen yet:

1. **Wired into `__main__.py` itself** — the same `python -m speakeasy` process runs both the
   menu-bar dictation client AND the HTTP server (in a background thread, alongside the
   TailnetProber). Simplest to launch (one process, one command), but ties the STT service's
   uptime to the GUI app's uptime — if the user quits the menu-bar app, the box stops being an
   inference host for others too, which may or may not be intended.
2. **Separate long-running script/service** (e.g. `python -m speakeasy.service`, or a systemd
   user unit) — decouples "is this box available as an inference host" from "is the user
   actively running the dictation app right now." Matches how the always-on Pi would eventually
   want to run it (once R-02 releases), but is a second thing to install/manage on every host
   that wants to serve.
3. **Hybrid**: `__main__.py` starts it by default but the setting is togglable, independent of
   whether the app is otherwise running.

No strong recommendation from this session — this is a genuine product-shape decision
(whether "runs the STT service" and "runs the dictation client" are the same on/off switch or
two), not a technical one, and the answer differs for a laptop (Mac, mostly client) vs. an
always-on box (Pi, mostly host) vs. this box (plausibly both). Flagging for your ruling or the
operator's.
